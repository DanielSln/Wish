# Fase 6.2 — pesquisa de APIs de preços

Consulta documental em 19/11/2026. Somente fontes oficiais; nenhuma conta/chave criada, serviço contratado, integração ou consulta autenticada implementada. Não foram sondados endpoints de produtos nem contornados bloqueios. Disponibilidade da documentação não comprova que o Wish obteria acesso.

## Conclusão

Não foi confirmada uma API gratuita, irrestrita e confiável que ofereça comparação multiloja brasileira para uma APK pessoal distribuída fora das lojas. Há APIs reais, mas com escopos comerciais, afiliação, catálogo de uma loja ou contrato. Manter ofertas manuais e importação revisada é a opção indicada agora. Isso é uma avaliação técnica com base nas evidências abaixo, não declaração de inexistência de qualquer API no mercado.

## Arquitetura futura recomendada — proposta, não implementação

Para fontes que exigem segredo, usar um backend mínimo com adaptadores por provedor, tokens em secret store, rotação/revogação, autorização mínima e limites de uso. Nunca embutir client_secret, chave de feed ou conta de serviço no APK. Custo de hospedagem/cache e manutenção depende do provedor; não há contratação autorizada. Fontes realmente públicas só poderiam ser acessadas diretamente após validar termos, destinos e limites.

O app enviaria apenas identificadores do produto/variante necessários à consulta; jamais catálogo completo, fotos privadas, notas pessoais ou credenciais. Não enviar dados pessoais/localização sem necessidade e consentimento. Reduzir logs, definir retenção e exigir HTTPS. Essa arquitetura é recomendação nossa, não requisito confirmado para todas as APIs.

Normalizar futuro resultado como: provedor, ID exato/GTIN/SKU/variante, vendedor, novo/usado/kit, moeda, preço comum/condicionado, texto de condição, URL original, instante de coleta, validade e origem. Separar coleta de persistência; pedir revisão antes de substituir referências/ofertas manuais. Preservar parâmetros legítimos e atribuição exigida, sem remover tokens de navegação de forma arbitrária. Não gravar segredos em URLs de logs.

Combinar apenas identidade comprovada, nunca nomes parecidos. Preservar avisos de disponibilidade/preço observado, contexto de pagamento/região/frete e resultado desconhecido. Um menor número não basta para declarar menor custo final: frete, impostos, quantidade, região e elegibilidade podem ser diferentes. Não calcular cupom implicitamente.

Respeitar 403, 429, CAPTCHA e autorização: interromper ou apresentar alternativa manual, sem rotação de identidades/proxies para contornar proteção. Cache/TTL precisam obedecer contratos; nenhum TTL universal foi validado aqui. Só dizer atualizado após consulta bem-sucedida identificada, sem garantir que checkout manterá valor.

## Próximos passos possíveis

1. Escolher uma fonte e confirmar por escrito o uso pessoal, distribuição privada, direitos de exibição/cache e cobertura brasileira, sem criar conta/contrato automaticamente.
2. Confirmar tarifas, limites, renovação de acesso e política de afiliação da conta real. Marca presente em uma rede não garante acesso ao programa.
3. Provar identidade de uma única variante e modelar frete/condicionais/indisponibilidade; mock antes de qualquer integração.
4. Apresentar arquitetura/custos e pedir autorização específica. Se mudar persistência, propor esquema/migração previamente.
5. Só então realizar prova técnica limitada, mantendo modo offline e cadastro manual. Nada disso foi implementado na Fase 6.2.
